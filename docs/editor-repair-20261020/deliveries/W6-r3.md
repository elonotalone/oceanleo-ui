# W6-r3 delivery — hosted deck toolbar/review, no synthetic human origin

## Root causes

W6-r2 made hosted deck send `selection-command`, but two things were still wrong:

1. **Synthetic human origin.** `buildDeckHostedCommandSurface.run` defaulted `origin: "user"`, and `sendHostedSelection` stamped every outgoing envelope `user`. Parent immediately set the planner origin to `null` (`bf53f828`). That refuse-closed the agent path; it did not give users a button.
2. **No actual edit bar.** `DeckHostedRoute` had no `renderContextToolbar` / shared bar. The only mutation path was the agent surface. A helper called from a test is not a working user button.

Integrity, CAS, origin set, sandbox, and permission checks were not loosened. pptist-hosted was not edited.

## What users get

On the hosted deck **normal** page (`resolveEditorCore` next), a selected PPTist object shows the shared edit-bar fill control. Clicking it posts `selection-command` with that object's id/revision and envelope `origin: "user"`. Pro mode keeps native PPTist chrome. No object selected → “请先选中对象再改格式。”, not a fake `slide-1` target. `view_only` / `access.canEdit === false` artifacts stay read-only.

Agent `deck.format-fill` ignores `params.origin`. A forged `origin:user` still sends an **unstamped** envelope (PPTist parks review). The run result is `applied: false`, `reviewed: true`. Sending is not treated as applied.

## Fixes

- Human send is only `sendDeckHostedHumanSelectionCommand` from the toolbar callback, which requires a real human stamp and uses W5 `onSelectionInteractionChange` → `applySelectionInteractionHold` / `selectionDuringInteraction`.
- Agent surface uses `sendAgent` / `planDeckHostedAgentSelectionCommand`. It never calls `hostedDeckHumanOrigin(params)` and never does `|| "user"`.
- Closed PPTist control ids only (`shape-fill`, `text-color`, …). r2 `fill` / `edit-text` / `slide-1` are gone.
- `deckHostedItemReadOnly` reads artifact `editability` and `access.canEdit`.
- `DeckHostedContextToolbar` renders the shared `SelectionToolbarControl`s and the shared edit-bar hold session. It does **not** import `SelectionToolbar.tsx` itself: that file publishes to agent-review, and compiling `DeckHostedRoute` with the existing G4/D1 hosted-editor stubs would rewrite `validReviewProposal` to a hole. Parent can later stub those tests or split the review publish out of `SelectionToolbar` if the wrapper component is required by name.

postMessage still uses the exact editor origin (UC-6). Sandbox token string unchanged.
