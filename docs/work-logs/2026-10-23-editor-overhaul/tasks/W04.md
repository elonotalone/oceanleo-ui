# W04 — 保存内核：每次保存都成为新版本、只 fork 一次、状态诚实、不再一存一个隐藏 root（D11 D13）

## 用户看到什么（完成后）

- 在任何编辑器里连着改、连着自动保存，每一次「已保存」都对应服务器上的一个新版本。关掉再开，看到的是最后一次的样子。
- 从素材库或公共素材打开别人的文件：第一次改动在我的库生成**一份**副本，编辑器和地址栏切到这份；之后的保存都进这一份，不再新增条目。
- 没确认的保存绝不显示「已保存」。失败时显示人话原因和「重试」。
- 保存不再在库里一次次留下隐藏的中间文件。

## 已知事实（父 agent 已查）

- [实测，生产库只读] 操作员 10-23 03:29Z 编辑 PDF `a3b9385f-df44-4918-9e6e-d3f62fac4473`：
  - 3 次自动保存都上传了 PDF 字节，每次都新建了一个隐藏的 `…-Edited` root（`metadata.editorInternal=true`，时间 03:29:11 / 03:29:20 / 03:29:47）。
  - 只有第 1 次成了 revision 3（03:29:13，digest 与第 1 次上传相同），后两次没有成为任何版本。
  - 10-22 13:46–13:48Z 的情形一样：3 次只成 1 次。
  - 其它编辑器也是「上传次数远多于新版本数」，例如某 md 文档 3 天上传 60 次、新版本 3 个，某音频 45 次对 2 个。哪些是附带文件、哪些是丢失的保存，由你在验收账号上分清。
- [读码] 根因候选，第一嫌疑：
  - `advanced-session.ts::advancedSavedItem(item, {url, versionId, meta})` 返回 `{...item, id: versionId, …}`，**`revisionId` 不变**。
  - `doc-io.ts::savedIdentity(item)` 读的是 `item.revisionId || item.meta.revision_id`，作为 commit 的 `expectedRevisionId`（CAS，后端 `If-Match`）。
  - 所以第 2 次保存拿旧版本当基线 → 409 冲突 → `fail("revision-publish")`。这时字节已经上传，留下一个孤儿 root。
  - 9 个路由都用 `advancedSavedItem`：Pdf、Deck、RichDoc、Audio、VideoTimeline、Model3D、Game、GridUniverStage、GameCodeStage，另有 `image-save-receipt.ts`。
- [读码] commit 在 `doc-io.ts` 约 1021 行调 `artifact-client.ts::createArtifactRevision`，后端是 `artifacts_router.py::save_revision` → `artifact_service.commit_revision`。上传各步（工程 JSON、交付件、预览）在同一个文件前半段，每步都会产生隐藏 root。
- [实测] 操作员库里现有 1,431 个 `editorInternal=true` 的 root。
- [读码] 已有私有 staging：`backend/app/editor_private_staging.py`，以及 10-22 给视频做的 staging → revision 闭包。
- [读码] 顶栏保存状态由 `use-advanced-autosave.ts` 的 state 驱动，经 `AdvancedWorkspaceActionBar`（W01）显示；`persistence.confirmation` 那条路给 hosted 件用。

## 要做

1. **复现**（先于任何修改）。验收账号上传 `[W04] sample.pdf`，在 PDF 编辑器里连续做 3 次改动，每次都等自动保存，然后查库：3 次上传、几个 revision、几个隐藏 root。浏览器场景存档到 `evidence/W04/scenarios/`。再用一种 doc-io 路径的编辑器（文档或演示）复现一次。
2. **基线前移**：
   - `advancedSavedItem` 带上新的 `revisionId`；如果能拿到完整返回 item（doc-io 的 `result.item`），就以它为准合并，`artifact` 对象里的 revisionId 和 renditions 也要更新。
   - doc-io 加兜底：本标签页对某 artifact 提交成功后记下 head；下次保存若基线比它旧且 409，就用记下的 head 重试一次（只认本标签页自己提交的 head，别人的不认，冲突照报）。
   - 测试同时覆盖两条路。
3. **只 fork 一次**：
   - 找到「不是自己的素材第一次保存」的路径（ensure / fork；客户端 `advanced-session` / `artifact-client`，后端 `fork_artifact`）。保证同一编辑会话只 fork 一次，之后的保存基线是 fork 出来的 revision；地址栏 `?item=` 换成新的 artifact id。
   - 用验收账号从公共素材打开一份（素材库或探索页挑一份公共演示或图片），改 3 次，查库：恰好 1 个新 root，且有 3 个 revision。
4. **中间文件**：
   - 保存时上传的工程 JSON、交付件、预览不再一次一个库 root，改走私有 staging，由 revision 的 blob claims 持有。
   - 如果后端合同做不到，至少每个 artifact 复用同一个内部 root、用 revision 前进，并写清楚取舍。
   - 不许让现有的文件丢 rendition。
5. **状态诚实**：
   - 「已保存」只在 commit 返回 `ok` 且校验通过之后出现。失败时状态为 `error`，带人话原因，顶栏可以重试。断网要有明确原因。
   - 保存期间关闭编辑器：沿用现有的后台保存与恢复快照，不拦用户，但失败要在库里看得到并能重试。
6. **透传接口**：`SaveToLibraryInput.artifactRevision.metadata?: Record<string, unknown>` → commit `content.metadata`（`backend ArtifactContentInput.metadata` 已有）。W08 用它存 `text_excerpt`。落地后在 `signals/W04-to-W08.md` 告诉它。
7. **清理脚本** `backend/scripts/editor_overhaul_cleanup_20261023.py`：
   - 默认 dry-run，输出两张清单：
     - 操作员账号的 4 个可见测试残留：`[Editor repair acceptance 2026-10-22] 23fafdea`、`[Editor repair video acceptance 2026-10-22] afb9aa8b`、`[客户端验收] 图片`、`upload-400-probe`，外加 10 个同源隐藏项。
     - 「没有任何现存 revision 引用」的 `editorInternal` root。引用关系要按 rendition、blob claim、`editor_manifest` 等实际字段判；判不清的一律归「保留」。
   - `--apply` 才退役。**你只跑 dry-run，`--apply` 只由父 agent 跑。**
   - dry-run 的结果（计数和抽样）写进交付。
8. **后端**：改了就在 journal 记一行，然后 `docker restart oceanleo-api`（批量后再重启）；pytest focused tests 要绿。
9. **浏览器验收**：保存协议 §5 第 1、3、4、5 条，至少覆盖 PDF、文档、演示、图片四件；每一件的数据库核对写进交付。

## 边界

- 编辑器路由文件归各编辑器 owner。
- 你发现某个路由另有一条「拿旧基线」的路径时，写 `signals/W04-to-Wxx.md`，写清具体位置和改法，由那位改。
- 你自己的修复要让 9 个路由**不改代码**就能保存成功，这就是第 2 步兜底的意义。
